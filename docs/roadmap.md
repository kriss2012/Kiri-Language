# Kiri Development Roadmap

This roadmap defines the engineering phases, dependencies, test criteria, and completion conditions for the Kiri programming language ecosystem.

---

## Roadmap Phases

| Phase | Title | Features | Dependencies | Test Strategy | Completion Criteria |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Phase 1** | **Bootstrap Core & Execution Engine** | Project skeleton, CLI (`kiri run`, `kiri repl`), source reader, lexical scanner with indentation handling, recursive-descent parser, AST, symbol resolution, unboxed primitives (Int, Float, Bool, Null), string literals, variables, arithmetic & comparisons, control flow (`if`/`elif`/`else`, `while`), functions, return, recursion, rich source diagnostics, REPL | None | Unit tests for lexer, parser, interpreter; integration tests for control flow and recursion; differential verification | Executes `factorial(10) == 3628800` via CLI and REPL; rich diagnostic errors rendered with source context. |
| **Phase 2** | **Collections, Object Model & Stdlib Foundations** | Lists, Tuples, Dictionaries, Sets, `for..in` loops, ranges (`0..10`), basic classes, methods, instance attributes, properties, module imports (`import`, `from`), exceptions (`try`/`except`/`finally`), basic builtins (`len`, `range`, `print`, `type`) | Phase 1 | Collection operation suites, object shape test cases, exception unwind tests, module resolution tests | Object-oriented and data-processing programs run with fast property lookups and deterministic exception unwinding. |
| **Phase 3** | **Type System & Strict Mode** | Local type inference, explicit type annotations, `strict` mode enforcement, generic collections (`List[Int]`), union types, `Option[T]` and `Result[T, E]`, structural & nominal protocol checks | Phase 2 | Semantic type analysis tests, positive/negative typecheck suites, compile-time error diagnostics | `strict` mode catches mismatched types before execution; zero runtime penalty for type declarations. |
| **Phase 4** | **Kiri Intermediate Representation (KIR) & Bytecode VM** | Lowering AST to linear KIR, optimization passes (constant folding, dead-code elimination, inlining), bytecode emission, stack-based/register VM, inline caching for method/field lookups | Phase 3 | Differential testing (AST Interpreter vs Bytecode VM), optimizer verification tests, execution benchmarks | Bytecode VM executes faster than tree interpreter with 100% semantic equivalence. |
| **Phase 5** | **Concurrency & Multithreading** | Free-threaded execution without GIL, green tasks / async-await event loop, structured task nurseries, message-passing channels, synchronization primitives (`Mutex`, `Atomic`) | Phase 4 | Multithreaded stress tests, race condition validation, parallel loop benchmarks (1, 2, 4, 8 cores) | CPU-bound parallel workloads demonstrate linear speedup across CPU cores. |
| **Phase 6** | **Tooling & Package Ecosystem** | Unified CLI (`kiri test`, `kiri fmt`, `kiri lint`, `kiri doc`, `kiri debug`), project manifests (`kiri.toml`), lockfiles (`kiri.lock`), automatic virtual environment isolation | Phase 5 | CLI workflow tests, formatting idempotency tests, linting rule verification | A complete project can be initialized, formatted, linted, tested, and locked with single commands. |
| **Phase 7** | **AOT Native Compilation & JIT** | Native code generation (LLVM / C emission / machine code), adaptive JIT tier for hot functions, FFI for C/C++/Rust interop | Phase 5 | Benchmark comparisons against C/Rust/Python, memory profiling, FFI call verification | Standalone native binary produced with `kiri build --release` without external runtime dependencies. |
| **Phase 8** | **Self-Hosting** | Re-implementing Kiri lexer, parser, typechecker, and compiler components directly in Kiri | Phase 7 | Bootstrap compiler compiles self-hosted compiler; self-hosted compiler compiles itself (stage 2 == stage 3) | Kiri compiler successfully builds itself. |
